# Launch buyer accounts and owner activity

The implementation is prepared locally; it is not deployed by saving cloud environment settings. The public Sites storefront and Railway backend are separate projects. The storefront currently sends purchases to Instagram, and the deployed backend currently returns 404 for `/account/` and `/api/v2/catalog`.

1. Obtain deployment access to the existing Railway backend and editing access to the Sites storefront. Preserve existing production bindings. Do not create replacement bots, databases or tokens merely because the cloud development machine has no production credentials.
2. Recommended mail setup: create or use the owner's Resend account, verify the sending domain using the exact DNS records shown there, and create a sending API key scoped to that domain. In Railway set `MAIL_PROVIDER=resend`, `RESEND_API_KEY` and `SMTP_FROM=Routine Pack <orders@routinepack.download>` (only after that domain is verified). Preserve `ADMIN_EMAIL` as the owner's intended mailbox. Keys belong in Railway's private Variables, never in chat or frontend source. The account uses email links rather than passwords. Existing Gmail OAuth and SMTP remain supported alternatives; do not rely on a Google external app's Testing consent for a permanent launch.
3. Configure the existing private Drive reader service account in `GOOGLE_SERVICE_ACCOUNT_JSON`, share the private source folder with that account, and verify `COMMERCE_FILES_JSON` covers each offered product. Preserve previously issued buyer links until deliberately migrated.
4. Back up the production database. Run `node scripts/migrate.js` on a separate staging database, then through the authorized production deployment workflow before deploying this code. The migration is additive and repeatable; the new `customer_activity` table is required by this bot version even with buyer accounts disabled.
5. On the server, run `node scripts/check-account-config.js`. It prints names and status only and makes read-only schema checks. It does not send mail, validate live Gmail/Drive access, migrate the database, register a webhook or turn accounts on. A missing-product report is a rollout gate for a full-catalog launch.
6. Run `node scripts/check-drive-files.js` in the Railway server environment before enabling buyer accounts. It authenticates with the read-only Drive scope, checks every offered product's mapping and download capability, and reads the start of each mapped file, cancelling the stream afterwards. It prints product codes and pass/fail only, never file IDs, credentials or file contents. It does not verify public-sharing settings: separately ensure the source folder/files remain restricted. Then validate sign-in and private file delivery in staging with actual server credentials and an owner-controlled test buyer. Confirm the bot's live `getMe` identity and owner chat, a confirmed registration, cart additions/removals, order creation, owner approval, buyer purchase email and one-use download. Keep acquiring off. Do not grant a purchase on order creation alone.
7. Deploy the validated backend configuration with `COMMERCE_ENABLED=true`, `TELEGRAM_ENABLED=true` and `WEB_ORIGIN` pointing to the verified backend HTTPS origin. Link the separate Sites storefront to the backend `/account/` portal and test the complete flow from `routinepack.download`. Do not embed server credentials or Drive IDs in Sites.

Until acquiring exists, the owner verifies payment outside the application and confirms the order in the bot. The customer then receives an email linking to the protected account library. FOP and acquiring are later work. Do not describe manual approval as automatic bank payment confirmation.
